# SEC-14 — Revocable biometric sign-in: review, design and risks

Written 10 Nov 2026 before any SEC-14 code was changed. Phase 1 (verification run 2, commit `56a077c`) is complete: analyzer 0 issues, 84 Flutter tests, Android debug APK built (`targetSdkVersion 36`), iOS release build, 75 fake-DB backend tests.

## 1. How biometric sign-in works today (reviewed in code)

| Question | Finding | Where |
|---|---|---|
| What is stored on the phone? | The member's **email and plain password**, under `bio_email` / `bio_password` | `lib/services/biometric_service_native.dart` |
| Where? | `flutter_secure_storage` — iOS Keychain (`first_unlock_this_device`), Android EncryptedSharedPreferences | same |
| What does the fingerprint/face check do? | It is an app-level gate (`local_auth`). On success the app reads the stored password and calls the normal `/auth/login`. The stored secret is **not** bound to biometrics by the operating system | `login_page.dart` `_handleBiometricLogin` |
| When is it stored? | Automatically on any password login with "Keep me signed in" ticked | `login_page.dart` `_handleLogin` |
| Does the server know a device is enrolled? | No. There is no server record, so nothing can be listed or revoked | — |
| Is anything device-bound? | No | — |
| Expiry? | None. The stored password works until the password changes | — |
| Logout | Client-only. Clears the session; **keeps** the stored password so Face ID can sign back in. There is no server logout endpoint | `auth_service.dart` `logout` |
| Password change / reset | Old tokens are refused (`token_version`, SEC-16). The stored password simply stops working; it is not removed from the phone | `routes/auth.py` |
| Settings toggle | Sets a flag only. Turning it off does not delete the stored password | `settings_page.dart` |
| Access tokens | Stateless JWT, 48 h for members, 8 h for admin roles, carrying `tv` (token version). Revoked only by bumping `token_version`, which signs out every device | `routes/auth.py`, `server.py` |
| Other | `isBiometricAvailable()` returns `true` when the platform check throws; the member's identifier is written to the debug log on enrolment | native service, login page |

### Risks in the current design

- **Password theft.** Anyone who can read the app's secure storage (rooted/jailbroken phone, device backup extraction, malware with the app's identity) gets the real password — usable on any device and on any other site where the member reused it.
- **No revocation.** A lost phone can only be cut off by changing the password.
- **No expiry, no device binding, no audit trail.**
- **Replay.** The password can be replayed indefinitely from anywhere.

## 2. Design

Replace the stored password with a random, server-issued, per-device credential that the server can list, expire and revoke. No biometric data ever leaves the phone; the server never receives or stores a fingerprint, face template or any derivative, and "biometric passed" is never accepted as proof by itself — the proof is possession of the device credential.

### Server

Table `biometric_tokens` (created idempotently in `init_db`):

| Column | Purpose |
|---|---|
| `id`, `member_id` (FK, cascade) | owner |
| `device_id` | random identifier generated by the app at enrolment |
| `device_name`, `platform` | shown to the member/admin; informational |
| `token_hash` | SHA-256 of the current 256-bit secret. The secret itself is never stored |
| `prev_token_hash` | hash of the previous secret, to detect reuse of a rotated token |
| `token_version` | the member's `token_version` at enrolment |
| `created_at`, `last_used_at`, `expires_at` | lifetime (default 90 days from enrolment, `BIOMETRIC_TOKEN_TTL_DAYS`; not extended by use) |
| `revoked_at`, `revoked_reason` | revocation |

Endpoints (all under `/api/v1/auth`):

| Endpoint | Auth | Behaviour |
|---|---|---|
| `POST /biometric/enroll` | access token **and current password** | Members only (admin roles refused). Creates a credential for `device_id`, replacing any existing one for that device. At most 5 devices per member; the oldest is revoked. Returns the credential once |
| `POST /biometric/login` | none (the credential is the proof) | Validates, **rotates** the credential, returns the same response as `/login` plus the new credential |
| `POST /biometric/revoke` | access token, or the credential itself | Revoke this device, or all devices |
| `GET /biometric/devices` | access token | List the member's enrolled devices (no secrets) |
| `POST /logout` | access token | `forget_device` revokes this device's credential; `all_devices` signs out everywhere (bumps `token_version`, revokes all credentials). A plain logout leaves the credential valid, by design — that is what lets Face ID sign back in |

Validation order for `/biometric/login` (row locked with `SELECT … FOR UPDATE`, so two simultaneous uses cannot both succeed):

1. Unknown id, or revoked → refuse.
2. Secret matches `prev_token_hash` → **reuse of a rotated token**: revoke the credential, refuse.
3. Secret does not match → refuse; after 5 wrong attempts the credential is revoked.
4. `device_id` differs → revoke, refuse.
5. Expired → revoke, refuse.
6. Member missing, deleted, suspended, inactive, unverified, or an admin role → refuse.
7. Member's `token_version` differs from the credential's → revoke, refuse.
8. Otherwise rotate (new secret, old hash moved to `prev_token_hash`) and sign in.

Every refusal returns the same generic message and `error_code: BIOMETRIC_TOKEN_INVALID` (403 with the usual message for suspended/inactive accounts), so the response does not reveal which check failed.

Automatic revocation of all of a member's credentials: password change, password reset, confirmed email change, account deletion, "sign out everywhere". Suspension blocks use without revoking.

### App

- Secure storage holds `bio_device_id` and `bio_token` only. On first launch after the update the legacy `bio_email`/`bio_password` are deleted and biometric sign-in is switched off until the member next signs in with their password.
- Enrolment happens after a password sign-in with "Keep me signed in" (the password is in memory at that moment), or from Settings after re-entering the password.
- Biometric sign-in: local biometric check → `POST /biometric/login` → store the rotated credential.
- A `BIOMETRIC_TOKEN_INVALID` answer deletes the local credential and asks for the password.
- Turning the toggle off revokes on the server and deletes locally. Changing the password in the app re-enrols this device with the new password.

## 3. Threats and how the design answers them

| Threat | Before | After |
|---|---|---|
| Secure storage read by an attacker | Real password exposed | A device credential only; revocable, expires, useless once the real app next signs in (rotation → reuse detection) |
| Stolen credential replayed from another device | n/a | Works at most until the real device next uses it, then both are cut off. `device_id` is copied with the credential, so device binding is **not** a defence against a full storage copy — rotation is |
| Lost or stolen phone | Change password | Revoke that device (or all) from another session; password change also revokes |
| Stolen 48 h access token used to mint a long-lived credential | n/a | Enrolment requires the current password |
| Guessing | — | 256-bit secret; IP rate limit; 5 wrong attempts revoke the credential |
| Privilege escalation | — | Credential yields only a normal member session with the member's current role and `token_version`; admin roles cannot enrol or use it |
| Database leak | Password hashes | Only SHA-256 hashes of high-entropy secrets |
| Race / double use | — | Row lock; second use sees a rotated token |

## 4. Residual risks and limits (not solved by this change)

1. **No hardware binding.** The credential is protected by the OS keystore, but the biometric check remains an app-level gate; the key is not tied to biometric enrolment by Keychain access control / Android `BiometricPrompt` crypto objects. A real fix needs a device-held key pair and signed challenges (native code). Consequence: adding a new fingerprint in system settings does not invalidate the credential.
2. **Lost response.** If the network drops after the server rotates but before the app stores the new credential, the next attempt looks like reuse and the device is cut off; the member signs in with the password once. Fails safe.
3. **Access tokens are still stateless.** A plain logout does not invalidate the 48 h access token on the server; only "sign out everywhere" and credential changes do.
4. **A member whose phone is stolen while unlocked** and whose biometrics are spoofed can sign in until the device is revoked — inherent to biometric convenience sign-in.
5. **No admin screen** for viewing/revoking a member's devices yet (API only).
6. **90 days** is a policy choice; shorten with `BIOMETRIC_TOKEN_TTL_DAYS`.
